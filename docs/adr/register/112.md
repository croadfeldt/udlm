**StorageLayout dissolves into Machine.** Machine 2.4.0 lists disks in `disks`: each a stable `name`, a `size`, an optional governed `storage_tier` and a `role`; `boot` marks the OS disk. Every platform declares disks on the machine, volumes apart; UDLM does too. StorageLayout was that part made a record; BareMetalHost and LPAR never referenced one. Boot order is the machine's firmware concern, not a disk's. Machine `boot_order` is an ordered list of `disks[].name` or the device class `network` or `cdrom`, as libvirt, KubeVirt, VMware and Redfish do, replacing Machine.VM `boot_order` and the per-entry position. A Volume joins a disk through `disk_entry` and the `realizes_disk` edge (Volume 0.14.0); `outputs.realized_volumes` is derived from those edges, never stored. Machine.VM 2.4.0 drops `layout_ref` and the `storage_layout` edge. The class is retired in `registry/renames.yaml`; the app01 worked records are re-issued. The field test (row 108) found the separation did not earn its place. Maintainer ruling 2026-10-25.
