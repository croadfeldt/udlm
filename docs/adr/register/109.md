**A subscription has no status field of its own.** Its status enum restated the four states (`PENDING` was Intent or Requested, `PROVISIONING` Requested, `ACTIVE` Realized, the decommission values Decommissioned) and a tier change is a new request. What remained has other homes: what the consumer wants is `desired_state` (`active`, `suspended`, `cancelled`), a spec element like Machine.VM's `run_state.desired_state`; renewal due and expiry are derived from the terms, never stored. Subscription-lifecycle §4 now says so with a table from each older value to its home, and the events table states its triggers that way. The first case of row 108. Closes #653.
